# ADR-0007: Frontend core package and workflow boundaries

**Status:** Accepted

**Date:** 2026-09-20

**Amended:** 2026-09-29

**Supersedes:** [ADR-0001](./0001-api-client-transport-and-operation-modules.md)

Calibrate needs one portable package for the shared frontend behavior of web and future React Native clients, not merely an HTTP client. Rename `@calibrate/api-client` to `@calibrate/frontend-core`. Preserve ADR-0001's stateless transport injection and app-owned `QueryClient` setup, but make the package's public boundary cohesive portable verticals and user-goal feature workflows rather than API-contract response types.

## Decision

- The package is `packages/frontend-core`, named `@calibrate/frontend-core`. It has no root public barrel: consumers use explicit approved leaf imports. The export map permits public vertical modules, feature workflows, transport/error modules, and co-located `__mocks__` test paths; it does not export `src/api/**`.
- `src/api/<area>/<endpoint>.ts` is private endpoint code. It owns route/path/query details, HTTP method, request-body validation, transport execution, response validation, and a pure mapper to frontend-domain data. The request operation returns the validated API response; it does not call the mapper. Define a response-to-domain mapper here, export it within core for the owning workflow to call, but `api/**` is not a public package path. The file contains no TanStack Query options or hooks, cache updates, or user-goal policy. Network and response-shape changes are localized beside the endpoint. It may depend on `@calibrate/api-contracts` and frontend-domain models; applications and vertical modules may not depend on API contracts.
- `src/feature-workflows/<workflow-group>/<goal>.ts` owns public application-layer orchestration for a cohesive user goal. It accepts frontend command inputs, maps them to API request shapes, calls private API operations, explicitly calls their co-located response mappers, and coordinates account context, TanStack Query options/hooks, cache updates required by that result, reconciliation, and fallback behavior as needed. For example, the sync, Save Food Entry, and Update Weight workflows each apply their own result to the Day Log cache. A workflow can use multiple verticals; its group need not match a vertical or endpoint. “Roughly one endpoint” is a default for organization, not a correctness constraint.
- `src/verticals/<area>/` groups functionality for one cohesive area that is portable between web and mobile. Purity is not an entry rule: a vertical may hold pure calculations, frontend-domain and portable presentation models, query-key families, reusable QueryClient cache observations/operations, and persistence policy when they belong to that area. For example, `src/verticals/day-log-cache/` may own shared Day Log keys, slot snapshots, freshness behavior, and persistence filtering/pruning; it need not collect result-application functions for unrelated workflows. `src/shared/models/` holds cross-vertical pure models and transforms. Vertical modules do not depend on API contracts or platform-specific browser/native APIs; endpoint response mappers stay in private API files.
- Core's portable Day Log persistence policy includes the cache buster, retention period, account-scoped dehydration allowlist, persisted-snapshot validation, and pruning. The consuming app supplies `ApiTransport`, account context or an accessor for it, and its `QueryClient`; core cache operations accept the app-owned client. A core workflow does not import the web authenticated-session hook.
- `DayLogSnapshot` is the cache-facing shared model: its data is `DayLog | null | undefined`, preserving the distinction between a loaded Day Log, a Known-empty day, and an unloaded day. `DayLog` initially retains the API-equivalent nullable meal collections; the endpoint's response mapper establishes the boundary without an unrelated shape redesign.
- Each app composes core's portable persistence policy with its own persister through `PersistQueryClientProvider`. The IndexedDB persister, durable cache-lifecycle fence, browser lifecycle events, router state, DOM APIs, WebAuthn adapters, and UI components stay in web; mobile supplies its own storage adapter and lifecycle integration. Core exposes an `AuthenticatedUserContext`; web session restoration remains the coordinator for browser cache fencing and navigation.
- Move portable behavior from web files such as `rank-recent-foods-from-cache.ts`, `confirm-food-nutrition.ts`, `log-page-helpers.ts`, and `day-log-cache.ts` into the core module that owns it, adapting API-contract inputs through endpoint response mappers before passing frontend-domain values to verticals. These are candidate sources, not instructions to move whole files: shared cache behavior and persistence policy from `day-log-cache.ts` can live under `verticals/day-log-cache/`, while `applyDayLogSyncResult`, `applyFoodEntryCreateToDayLogCache`, and `applyWeightObservationToDayLogCache` belong inside their respective `<goal>.ts` feature-workflow files because each applies that workflow's result. Keep route and display choices in web when they are specific to its UI; purity alone does not make them platform-specific. `indexed-db-day-log-cache.ts` and `browser-passkey-registration-adapter.ts` stay in web because they depend on browser APIs.
- `ApiTransport` credentials are app-configurable and default to the current `"include"` behavior. This preserves web cookies while leaving the future mobile authentication transport explicit.

For Save Food Entry, move `saveFoodEntry` to `src/api/day-logs/save-food-entry.ts`: it validates the body, forms `POST /daylogs/{date}/food-entries`, and returns the validated API response. Define the pure save-response mapper in that same file. Put `getSaveFoodEntryMutationOptions` and `useSaveFoodEntry` in `src/feature-workflows/day-logs/save-food-entry.ts`, together with the portable user-goal orchestration currently in web's `verticals/day-log-cache/use-save-food-entry.ts`. That workflow obtains host-supplied account context, executes the save, calls the mapper to turn its acknowledgement into frontend-domain data, applies the result to the account-scoped Day Log slot using shared cache keys/models, conditionally syncs an unverified date, and retains the local acknowledgement for later validation if reconciliation fails. The options factory and hook share the same workflow policy.

## Consequences

The web and mobile frontends can share tested request logic, frontend-domain data, TanStack Query behavior, and view-independent projections without sharing a browser runtime. A backend response change is normally localized to the private endpoint file and its response mapper rather than propagating through consumers. The workflow's internal import of that mapper is a deliberate dependency on private endpoint code, like its existing import of the request operation; the package export map keeps both inaccessible to apps. If the frontend-domain meaning changes, its model and consumers may also need changes.

The first migration checkpoint is intentionally mechanical: rename the workspace package and replace root imports with direct leaf imports before changing model behavior. Later checkpoints remove the temporary API-shaped public adapters, migrate every existing operation (including auth), and verify that application source has no `@calibrate/api-contracts` dependency for data received from core.

The Day Log IndexedDB persister and cache-lifecycle fence remain governed by [ADR-0004](./0004-bounded-day-log-sync-and-cache-fence.md) and its amendment [ADR-0006](./0006-logs-calendar-week-scroller-prefetch.md). This ADR moves portable in-memory cache composition and persistence policy to core; it does not weaken those privacy or freshness invariants.

## Considered options

- **Keep `@calibrate/api-client` as a request-only package:** rejected because shared frontend domain types, cache reconciliation, and reusable React Query workflows would otherwise fragment across apps.
- **Export raw API operations and contract response types:** rejected because consumers would remain coupled to backend response shape.
- **Put platform persisters and session gates in core:** rejected because IndexedDB, document/window events, router behavior, and cache-fence lifecycle are platform-specific. The persistence policy they enforce is shared in core.
- **Use a root barrel:** rejected because it obscures dependency ownership and makes accidental imports of internal or unrelated modules easier.
- **Put response mappers in feature workflows or separate mapper files:** rejected for endpoint-specific response conversion because the request and mapper should be found together when the server response shape changes. Workflows retain the decision of when to map and what to do with the result.
